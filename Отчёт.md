# Отчёт

## 1. Доменная область приложения

Приложение «Заметки» — простой сервис для ведения личных текстовых заметок. Пользователь регистрируется, входит в систему и управляет собственными заметками: создаёт, просматривает, редактирует и удаляет их. Заметки привязаны к владельцу, и каждый пользователь видит и изменяет только свои записи.

Приложение реализовано как клиент-серверное: серверная часть (бэкенд) предоставляет REST API, клиентская часть (фронтенд) — веб-страница, которая обращается к этому API. Данные хранятся в реляционной БД.

## 2. Стек реализации

| Компонент | Технология |
|---|---|
| Язык и платформа бэкенда | Java 22 |
| Фреймворк бэкенда | Spring Boot 3.3.4 (Spring Web, Spring Data JPA, Spring Security, Bean Validation) |
| ORM | Hibernate (через Spring Data JPA) |
| СУБД | PostgreSQL 16 |
| Миграции схемы БД | Liquibase (миграции в формате SQL) |
| Сборка бэкенда | Maven |
| Фронтенд | Статическая HTML-страница на чистом JavaScript (без фреймворков и сборки) |
| Веб-сервер фронтенда | nginx (образ alpine), он же проксирует запросы `/api/` на бэкенд |
| Контейнеризация | Docker (multi-stage сборка бэкенда), Docker Compose |
| Взаимодействие клиента и сервера | HTTP/1.1, REST, формат JSON, ошибки в формате RFC 7807 (`application/problem+json`) |
| Аутентификация | HTTP Basic, пароли хранятся в виде хэша BCrypt, сервер не хранит сессий |

Стек выбран нересурсоёмким: бэкенд запускается на облегчённом образе `eclipse-temurin:22-jre-alpine` с последовательным сборщиком мусора (SerialGC) и ограничением доли памяти, фронтенд — на `nginx:alpine` без сборки и Node.js.

## 3. Основные сущности доменной области

Схема БД описана в миграции `001-init.sql`. Связь между сущностями: один пользователь — много заметок (1:N).

### User (пользователь, таблица `users`)

| Поле | Тип | Описание |
|---|---|---|
| `id` | BIGINT, первичный ключ | Идентификатор (генерируется БД) |
| `username` | VARCHAR(50), уникальный | Логин |
| `password` | VARCHAR(100) | Хэш пароля (BCrypt) |
| `role` | VARCHAR(20) | Роль (перечисление `Role`, сейчас единственное значение — `USER`) |

Класс `User` реализует интерфейс `UserDetails` Spring Security, то есть служит одновременно сущностью БД и принципалом аутентификации вместо встроенного пользователя Spring.

### Note (заметка, таблица `notes`)

| Поле | Тип | Описание |
|---|---|---|
| `id` | BIGINT, первичный ключ | Идентификатор (генерируется БД) |
| `title` | VARCHAR(255) | Заголовок, обязательное поле |
| `content` | VARCHAR(4000) | Текст заметки, обязательное поле |
| `user_id` | BIGINT, внешний ключ на `users(id)` | Владелец заметки; при удалении пользователя его заметки удаляются каскадно |

### Операции над сущностями (REST API)

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `POST /api/auth/register` | Регистрация пользователя | без авторизации |
| `GET /api/auth/me` | Текущий пользователь (проверка входа) | авторизованным |
| `GET /api/notes` | Список заметок пользователя | авторизованным |
| `GET /api/notes/{id}` | Получить заметку | авторизованным |
| `POST /api/notes` | Создать заметку | авторизованным |
| `PUT /api/notes/{id}` | Изменить заметку | авторизованным |
| `DELETE /api/notes/{id}` | Удалить заметку | авторизованным |

Над заметками реализован полный набор CRUD-операций; обращение к чужой заметке возвращает 404.

### I. Кодовая база (Codebase)

Приложение хранится в одной кодовой базе (один репозиторий под управлением системы контроля версий) с каталогами `backend/` и `frontend/`. Из этой кодовой базы собираются одни и те же образы, которые можно развернуть сколько угодно раз (локально, на тестовом и боевом окружении). Различаются только конфигурация и окружение, код один.

### II. Зависимости (Dependencies)

Все зависимости бэкенда явно объявлены в `pom.xml`, версии управляются родительским проектом `spring-boot-starter-parent` (3.3.4), сборка воспроизводима командой `mvn package`. Приложение не полагается на библиотеки, установленные в системе: окружение целиком описано в Dockerfile (образы `maven:3.9-eclipse-temurin-22` для сборки и `eclipse-temurin:22-jre-alpine` для запуска). Фронтенд зависимостей не имеет (чистый JavaScript без внешних библиотек). Версия PostgreSQL зафиксирована в `docker-compose.yml` (`postgres:16-alpine`).

### III. Конфигурация (Config)

Всё, что различается между окружениями, вынесено в переменные окружения: параметры подключения к БД (`DB_URL`, `DB_USER`, `DB_PASSWORD`), порт (`PORT`), уровни логирования (`LOG_LEVEL`, `APP_LOG_LEVEL`), адрес бэкенда для nginx (`BACKEND_URL`), параметры контейнера БД (`POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`). Значения задаются в файле `.env`, который читает Docker Compose и передаёт их контейнерам; сам файл не попадает ни в образы, ни в репозиторий (указан в `.gitignore`). В `application.properties` значения по умолчанию указаны только как удобство для локального запуска; секретов боевого окружения в коде нет.

### IV. Сторонние службы (Backing services)

PostgreSQL подключается как присоединённый ресурс: приложение знает о нём только URL, логин и пароль из переменных окружения. Замена локальной БД на внешнюю (например, облачную) выполняется сменой `DB_URL`, `DB_USER` и `DB_PASSWORD` без изменения кода и пересборки образа. БД запускается отдельным контейнером и не является частью бэкенда.

### V. Сборка, релиз, выполнение (Build, release, run)

Этапы разделены средствами Docker:

- **Сборка.** Первый этап Dockerfile (`mvn package`) превращает код в исполняемый jar, второй этап копирует его в минимальный образ без инструментов сборки.
- **Релиз.** Образ вместе с конфигурацией из переменных окружения (`docker-compose.yml` и `.env`) образует релиз; образ неизменяем, конфигурация подставляется при запуске.
- **Выполнение.** `docker compose up` запускает контейнеры; код в работающем контейнере не изменяется.

Оговорка: в рамках учебного проекта не настроены CI/CD и версионирование образов (тегирование релизов), то есть нумерованных релизов и откатов на конкретный релиз нет. Принцип разделения этапов при этом соблюдён.

### VI. Процессы (Processes)

Бэкенд не хранит состояния между запросами: сессии отключены (`SessionCreationPolicy.STATELESS`), а каждый запрос содержит заголовок `Authorization` (HTTP Basic), по которому пользователь определяется заново. Всё постоянное состояние (пользователи и заметки) находится в PostgreSQL. Локальная файловая система контейнера для данных не используется. Фронтенд — статические файлы; данные входа хранятся только на стороне клиента (`sessionStorage` браузера).

### VII. Привязка портов (Port binding)

Бэкенд не требует внешнего сервера приложений: Tomcat встроен в Spring Boot, приложение само открывает порт, заданный переменной `PORT` (по умолчанию 8080). nginx самостоятельно слушает порт 80 внутри контейнера. Наружу через Compose опубликован только порт фронтенда (`3000:80`); бэкенд и БД доступны только во внутренней сети Compose. Фронтенд обращается к бэкенду по HTTP, то есть бэкенд сам является сервисом для других.

### VIII. Параллелизм (Concurrency)

Масштабирование выполняется процессной моделью: так как бэкенд не хранит состояния (фактор VI), его можно запускать в нескольких экземплярах (`docker compose up --scale backend=N`), запросы пользователя могут обслуживаться любым экземпляром без «липких» сессий. Запись в БД защищена транзакциями, а ограничение уникальности логина контролируется индексом в БД, поэтому параллельные запросы не приводят к дублям.

Оговорка: готовой конфигурации с несколькими экземплярами в проекте нет. nginx обращается к бэкенду по имени сервиса из `BACKEND_URL` и определяет адреса при старте, поэтому динамическая балансировка при изменении числа экземпляров не настроена. Для учебного приложения с минимальным функционалом это сознательное упрощение; архитектурных препятствий для масштабирования нет.

### IX. Утилизируемость (Disposability)

- **Быстрый запуск.** Приложение лёгкое и стартует за секунды; его можно без последствий запускать и останавливать в любой момент.
- **Корректная остановка.** Включён `server.shutdown=graceful`: при получении SIGTERM сервер перестаёт принимать новые запросы и дожидается завершения текущих. Dockerfile использует exec-форму `ENTRYPOINT ["java", "-jar", ...]`, поэтому JVM является главным процессом контейнера и получает сигнал остановки напрямую.
- **Устойчивость к внезапной остановке.** Операции изменения данных выполняются в транзакциях, поэтому обрыв процесса не оставляет БД в неконсистентном состоянии.
- **Запуск зависимостей.** Бэкенд стартует только после готовности БД (healthcheck и `depends_on` с `service_healthy`). Параллельный запуск нескольких экземпляров безопасен: Liquibase использует блокировку (`DATABASECHANGELOGLOCK`), поэтому миграции не выполняются одновременно.

### X. Паритет разработки и работы приложения (Dev/prod parity)

Окружения максимально совпадают: в разработке и эксплуатации используются одни и те же образы, одна и та же СУБД (PostgreSQL, а не подменяющая её встроенная БД вроде H2) и одни и те же миграции Liquibase. Различия сведены к конфигурации (фактор III). Запуск всего стека выполняется одной командой, что позволяет разработчику работать в окружении, идентичном боевому. Разрыв во времени между разработкой и выпуском небольшой, разработчики и эксплуатирующие совпадают (приложение учебное, развёртывается тем же человеком, который его пишет).

### XI. Журналирование (Logs)

Приложение не управляет файлами логов и не занимается их ротацией: все события выводятся потоком в стандартный вывод (stdout) — это поведение Spring Boot по умолчанию, зафиксированное в конфигурации. Сбор, хранение и анализ логов — задача среды выполнения: Docker перехватывает stdout контейнеров (`docker logs`, `docker compose logs`) и при необходимости передаёт его логирующему драйверу или внешней системе. Официальный образ nginx также направляет свои журналы в stdout/stderr. Уровни детализации меняются переменными окружения (`LOG_LEVEL`, `APP_LOG_LEVEL`) без пересборки. В журнал попадают значимые события: регистрация, создание, изменение и удаление заметок, отказ в доступе (401/403), конфликты и необработанные исключения со стеком вызовов. Пароли и другие секреты в логи не записываются.

### XII. Задачи администрирования (Admin processes)

Единственная административная задача приложения — миграция схемы БД. Она описана кодом (SQL-файлы Liquibase лежат в репозитории вместе с приложением), версионируется вместе с ним и выполняется теми же образом и конфигурацией, что и основное приложение: Liquibase запускается при старте бэкенда с тем же подключением к БД. Другие разовые операции (например, разовая команда в окружении приложения) можно выполнить тем же образом и теми же переменными окружения командой `docker compose run --rm backend ...`.

Оговорка: миграции выполняются при старте основного процесса, а не отдельным разовым процессом. Для приложения с одной простой схемой это оправданно (блокировка Liquibase исключает гонки между экземплярами); для крупных систем миграции принято выносить в отдельный разовый процесс.
